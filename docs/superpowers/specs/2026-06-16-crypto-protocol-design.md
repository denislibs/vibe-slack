# Криптопротокол — дизайн (подпроект 1 из 4)

**Дата:** 2026-06-16
**Статус:** утверждён
**Проект:** корпоративный мессенджер с E2E-шифрованием (production)

## Контекст

Часть платформы корпоративного мессенджера (аналог Slack с упором на безопасность).
Платформа декомпозирована на 4 подпроекта, каждый со своей спекой → планом → реализацией:

1. **Криптопротокол** (этот документ) — задаёт форматы данных для остальных
2. Бэкенд-транспорт на Go (сокеты + масштабирование)
3. Фронтенд-каркас на SolidJS (три потока)
4. UI/UX и анимации

Инфраструктура всей платформы: Docker, PostgreSQL (основное хранилище), Redis
(presence/кэш/pub-sub между нодами), RabbitMQ (очереди/доставка).

### Принятые решения

| Решение | Выбор | Обоснование |
|---|---|---|
| Цель | Production-платформа | Крипто и масштабирование делаем всерьёз |
| Модель E2E | E2E + комплаенс-аккаунт | Регулируемый корпоратив: сервер не читает, аудитор с депонированным ключом — может |
| Протокол | MLS (RFC 9420) | Современный стандарт группового E2E, обновление ключей за O(log N) |
| Мульти-девайс | Каждое устройство = отдельный leaf | Изоляция: компрометация одного устройства не раскрывает остальные |
| Идентичность | Своя аутентификация + Key Transparency | Без внешнего SSO; аудируемый лог ключей в стиле CONIKS/WhatsApp |
| Пароли | OPAQUE (aPAKE) | Сервер физически не видит пароль и не может сбрутить из БД |
| Комплаенс-участник | Видимый в составе группы | Сохраняет гарантии MLS (состав аутентифицирован), этически и юридически чище |

## Модель доверия и границы

**Принцип: сервер недоверенный.**

Сервер видит:
- метаданные (кто с кем в группе, эпохи, маршрутная информация)
- зашифрованные блобы сообщений
- публичные KeyPackages устройств

Сервер НЕ видит:
- содержимое сообщений
- приватные ключи устройств

**Не пишем собственную криптографию.** Используем проверенные примитивы:

- **OpenMLS** (Rust → WASM) — движок MLS на клиенте
- **libsodium** (через WASM) — вспомогательные операции (XChaCha20-Poly1305, X25519)
- **OPAQUE** (aPAKE) — аутентификация по паролю без раскрытия пароля серверу

### Три роли сервера (реализуются в подпроекте 2, Go)

1. **AS (Authentication Service)** — регистрация/вход через OPAQUE, выдача сессионных токенов
2. **DS (Delivery Service)** — приём/пересылка MLS-сообщений (handshake + application),
   хранение очередей. Полностью недоверенный.
3. **KT (Key Transparency)** — append-only Merkle-лог привязок «личность → ключи устройств»,
   подписанные Signed Tree Heads (STH)

## Компоненты и интерфейсы

| Компонент | Где живёт | Назначение | Зависит от |
|---|---|---|---|
| **Crypto Engine** | Клиент, WASM-воркер (3-й поток) | Весь MLS: создание групп, шифрование/дешифрование, ratchet, обработка Commit/Welcome | OpenMLS, libsodium |
| **Local Key Store** | Клиент (IndexedDB, зашифрован) | Приватные ключи устройства, состояние групп MLS | Crypto Engine |
| **AS** | Go-сервис | OPAQUE-регистрация/вход, JWT/сессии | Postgres |
| **KeyPackage Store** | Go-сервис | Публичные KeyPackages устройств (для добавления в группы офлайн) | Postgres |
| **KT Log** | Go-сервис | Merkle-дерево привязок, STH, доказательства включения для клиентов | Postgres |
| **Compliance Keystore** | Изолированный сервис | Депонированные ключи комплаенс-участника, доступ только аудитору с отдельной авторизацией | отдельная БД / HSM |

Каждый компонент имеет одну ответственность, общается через явные интерфейсы (см. ниже)
и тестируется независимо.

## Комплаенс-участник

В каждую группу MLS при создании добавляется дополнительный **leaf** — «комплаенс-устройство»
организации. Его приватный ключ хранится в изолированном Compliance Keystore (в идеале за HSM).

- Технически это обычный участник MLS → сервер по-прежнему не читает переписку.
- Аудитор, получив доступ через отдельную процедуру авторизации, может расшифровать архив.
- Присутствие комплаенс-участника **видно** в составе группы (прозрачность для пользователей;
  соответствует модели MLS, где состав аутентифицирован).

## Cipher suite

- **MLS cipher suite:** `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`
  (mandatory-to-implement, максимальная совместимость) с опцией перехода на XChaCha20-вариант.
- **Подписи устройств:** Ed25519.

## Контракты данных (границы с подпроектами 2 и 3)

### Крипто ↔ сеть/бэкенд

```
KeyPackage      — публичный, отдаётся в AS/KeyPackage Store (TLS-сериализация MLS)

MLSMessage      — handshake (Commit/Proposal/Welcome) ИЛИ application;
                  для DS это непрозрачный blob + минимум маршрутной метаинформации:
                  { group_id, epoch, sender_leaf, content_type, ciphertext }

KTProof         — { identity, leaf_pubkeys[], merkle_proof, sth_signature }

OPAQUE flow     — { registration_request/response, KE1/KE2/KE3 } (бинарные)
```

### Граница внутри клиента (UI-поток ↔ crypto-воркер)

Структурированные сообщения через `postMessage`:

```
→ encrypt(group_id, plaintext)        ← { mls_message_blob }
→ decrypt(mls_message_blob)           ← { sender, plaintext, epoch }
→ create_group / add_member / remove  ← { commit, welcome }
→ process_commit(blob)                ← { ok, new_epoch }
```

**Инвариант:** сырые ключи никогда не покидают воркер — наружу только шифртекст или
расшифрованный текст.

## Тестирование

- **Тест-векторы RFC 9420** — прогон официальных MLS-векторов через Crypto Engine
  (gate на корректность).
  - **Известное ограничение реализации (на openmls 0.6):** публичный runner векторов
    в OpenMLS 0.6 закрыт за `#[cfg(test)]` и не вызывается из внешнего крейта, поэтому
    наш gate выполняет *структурную* проверку (векторы завендорены и покрывают MTI-suite
    0x0001), а не исполняющий round-trip каждого вектора. Корректность примитивов при
    этом обеспечивается: (а) OpenMLS гоняет эти же векторы в собственном тест-сьюте
    апстрим, (б) наши собственные тесты движка делают реальные encrypt/decrypt round-trip
    и проверяют forward secrecy. При апгрейде openmls — пересмотреть, не появился ли
    публичный runner, и при возможности перейти на исполняющий gate.
- **Property-тесты** на инварианты: после Commit все участники приходят к одному
  epoch-секрету; удалённый участник не расшифровывает новые epoch'и
  (forward secrecy / post-compromise security).
- **OPAQUE** — сервер не хранит ничего, из чего восстановим пароль; неверный пароль
  неотличим на уровне сервера.
- **KT** — доказательства включения/консистентности проверяются; подделанный STH
  отвергается клиентом.
- **Комплаенс** — аудитор расшифровывает архив с депонированным ключом; без ключа — не может.
