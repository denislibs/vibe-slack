# Client MLS orchestration (6.3b) — дизайн

**Дата:** 2026-06-17
**Статус:** утверждён
**Проект:** корпоративный мессенджер с E2E-шифрованием (production)

## Контекст

6.3a дал крипто-примитивы (createGroup, addMember+Welcome, joinByExternalCommit, exportGroupInfo,
process/encrypt, compliance). 6.1 дал серверные беседы (DM/каналы, членство-юзеры, device-роутинг
гейтится членством). 6.2 дал `KTVerifier.verifyIdentity(identity) → verified signing keys`. 6.3b —
**оркестрация**: связать всё в реальные сценарии create / add-member / join-public / обмен, плюс
небольшие серверные эндпоинты, которых не хватает. UI — 6.3c.

### Ключевая развязка: добавление пользователя в группу

Чтобы MLS-добавить пользователя, добавляющему нужны **KeyPackages его устройств**. KT (6.2) даёт
только signing-ключи личности. Существующего `GET /keypackages/{device_id}` мало — нет способа
узнать device-id'ы чужого пользователя. Решение (рекомендуемое): новый эндпоинт **key-material по
личности**, который для каждого активного устройства цели отдаёт `{device_id, signing_public_key,
key_package}` (потребляя по одному KeyPackage на устройство). Клиент:
1. `verifyIdentity(identity)` (6.2) → доверенный набор signing-ключей;
2. сверяет, что `signing_public_key` каждого устройства ∈ этого набора (иначе — стоп, MITM);
3. MLS `addMember(key_package)` по каждому устройству; складывает device-id'ы в DS-ростер.

### Принятые решения

| Решение | Выбор | Обоснование |
|---|---|---|
| Получение ключей цели | `GET /workspaces/{wsId}/users/{identity}/key-material` → `[{device_id, signing_public_key, key_package}]` (consume по 1 KP/устройство) | KT даёт только signing-ключи; для MLS-add нужны device-KeyPackages |
| Authz key-material | caller ∈ WS И target ∈ WS | Нельзя тянуть ключи вне своего тенанта |
| KT-проверка | Клиент сверяет каждый device signing key ∈ verifyIdentity(identity) перед add | MITM-защита |
| Хранение GroupInfo | колонка `group_info BYTEA` на `conversation_meta`; `PUT/GET /conversations/{group}/group-info` | Нужен для external-join публичных каналов; публичен (ratchet tree) |
| Когда публикуем GroupInfo | После create и после каждого add/commit (для каналов; для public — обязательно) | Джойнеру нужен свежий GroupInfo |
| Комплаенс KeyPackage | `GET /keypackages/compliance` (KP заранее загруженной compliance-личности) | Видимый escrow-участник в каждой группе |
| Доставка commit/Welcome | Через готовый DS (отправка как сообщение по `group_id`; Welcome — по journal/`join_seq`) | Транспорт уже есть; новый член получает Welcome при join_seq |
| Кто мёржит/раздаёт | Добавляющий клиент: 6.1 add-user (членство) → MLS add → ростер (POST /members с join_seq) → отправка commit+Welcome | Единый инициатор |

## Область и границы

**В scope (6.3b):**
- **Backend:** key-material endpoint; GroupInfo column + `PUT/GET .../group-info` (gate by conv membership);
  compliance KeyPackage endpoint; `DeviceRepo` метод «активные устройства с signing-ключами».
- **Frontend `shared/api`:** клиенты для key-material, group-info (get/put), compliance KP.
- **Frontend `features`/`app` оркестрация:**
  - `createConversation(type, …)` → 6.1 create → MLS `createGroupWithCompliance` (или create+addCompliance) → publish GroupInfo.
  - `addMember(group, identity)` → 6.1 add-user → key-material → **KT verify each device key** → MLS add per device → DS roster (join_seq = текущий max seq) → отправить commit (всем) + Welcome (новым) → publish GroupInfo.
  - `joinPublic(group)` → GET group-info → MLS `joinByExternalCommit` → DS roster (свои устройства) → отправить external commit → (свежий GroupInfo подтянется при следующем изменении).
  - inbound: `commit` → `CryptoClient.decrypt`(process) ; `Welcome` (новый kind фрейма/доставки) → `joinFromWelcome`.
  - реальный обмен: текст → encrypt → DS send ; DS message → decrypt → conversation-стор (через готовый orchestrator).
- Тесты: backend integration; frontend use-case unit (моки Crypto/Proto/AS/KT/conv) + slice против мок-DS.

**Out of scope:** UI-экраны (6.3c); email-инвайты (7); Slack Connect (8); ротация ключей/обновление KT при
add (KT-relay уже подхватывает enroll'ы — повторная публикация версий вне области); перенос истории до входа;
устойчивость к гонкам эпох (DELIVERY CONTRACT из 6.3a: успешная доставка commit обязательна — best-effort).

## Контракты эндпоинтов (новые)

| Метод | Путь | Кто | Тело/ответ |
|---|---|---|---|
| GET | `/workspaces/{wsId}/users/{identity}/key-material` | caller∈WS, target∈WS | → `[{device_id, signing_public_key(b64), key_package(b64)}]` (по 1 consumed KP/активное устройство); 404 если target не в WS / нет устройств |
| GET | `/conversations/{group}/group-info` | член беседы / public+член WS | → `{group_info(b64)}` или 404 если не опубликован |
| PUT | `/conversations/{group}/group-info` | член беседы | `{group_info(b64)}` → 200; сохраняет последний |
| GET | `/keypackages/compliance` | любой аутентиф. | → `{key_package(b64)}` (KP compliance-личности) |

`conversation_meta` += `group_info BYTEA NULL` (миграция `0006_group_info.sql`).
Compliance: bootstrap — compliance-личность регистрируется и заливает KeyPackages как обычное устройство;
endpoint отдаёт `Consume` по её device_id (конфиг `COMPLIANCE_DEVICE_ID`/идентичность). Для v1 допустимо:
если compliance не настроен (env пуст) — endpoint 404 и клиент создаёт группу без compliance (с предупреждением),
чтобы не блокировать разработку; продакшн требует настроенного compliance.

## Обработка ошибок
- key-material: target не в WS → 404; нет активных устройств/KP исчерпаны → 404/409 (клиент ретраит/деградирует).
- KT-несовпадение signing-ключа устройства → клиент НЕ добавляет, помечает беседу как непроверённую, не молчит.
- group-info PUT от не-члена → 404; GET не опубликован → 404 (джойнер ждёт/ретраит).
- Доставка commit упала → лог + статус (DELIVERY CONTRACT: эпоха ушла вперёд; ретрай доставки).

## Тестирование
- Backend (testcontainers): key-material (authz WS, per-device KP consume, signing keys); group-info put/get + membership gate; compliance KP.
- Frontend use-cases (моки): createConversation последовательность; addMember — KT verify блокирует add при несовпадении, иначе add+roster+deliver+publish в правильном порядке; joinPublic — get-info→external-commit→roster→send.
